### 1.2 핵심 설계 방향

출근 기록의 원천은 MOA 밖(지문 단말)에 있고 퇴근 기록은 MOA 안(앱 버튼)에서만 생긴다. **MOA는 두 원천을 병합해 판정하는 계층**이다. 4계층으로 나눈다.

```
[출입문 지문 단말]  ─ 입장 이벤트만        [MOA 앱] ─ 출근/퇴근 버튼
      │  (어댑터: DB 폴링 / REST / CSV)          │
      └──────────────┬───────────────────────────┘
                     ▼
① 수집   att_raw_events  — 두 원천의 이벤트를 한 테이블에 무손실 적재 (멱등)
                     ▼
② 정규화 att_days        — 사람·날짜 단위로 접기 (출근=우선순위 병합 / 퇴근=앱)
                     ▼
③ 판정   근무·연장·야간·휴일 분(分) 계산, 주 52h·연차 판정
                     ▼
④ 보정   att_corrections / leave_requests — 사람이 고치고 팀장이 승인
```

**①을 ②·③과 분리하는 이유:** 판정 규칙(휴게 공제, 야간 기준, 지각 유예)은 취업규칙이 바뀌면 같이 바뀐다. 원본을 무손실로 남겨두면 규칙 변경 시 과거 데이터를 **재계산(replay)** 할 수 있다. 원본 위에 덮어쓰면 못 한다.

**두 원천을 한 테이블에 넣는 이유:** 지문과 앱은 신뢰도가 다를 뿐 같은 종류의 사실("이 사람이 이 시각에 여기 있었다")이다. 별도 테이블로 나누면 병합 규칙이 조인 쿼리에 흩어지고, 나중에 출구 리더기가 생기면(§13 I11) 세 번째 테이블이 필요해진다. `source` 컬럼 하나로 구분한다.

### 1.3 출입 시스템의 구조적 한계 — 이 설계의 대부분은 여기서 나온다

| # | 한계 | 대응 |
| --- | --- | --- |
| **L1** | **퇴근 기록이 없다.** 단말이 입장 전용이라 모든 지문 이벤트는 `direction='in'`이다 | 퇴근은 **앱 버튼이 유일한 원천**. 안 누르고 퇴근하면 미기록 → D2 플래그 + 다음날 보정 유도 (§5.2) |
| **L2** | **동반 입장 시 지문 누락.** 뒷사람이 안 찍으면 그날 출근 기록이 아예 없거나, 점심 후 재입장 시각이 첫 기록이 되어 **몇 시간 지각으로 오판** | 출근 시각 = `min(지문 첫 이벤트, 앱 출근 버튼)`. 앱 버튼이 지문 누락을 메운다 (§5.2) |
| L3 | 점심 외출·흡연·택배 수령 후 **재입장 이벤트** | 첫 이벤트만 채택. 중간 이벤트는 원본에 보존하되 판정에 미사용 |
| L4 | **외근·재택·출장 시 지문 기록이 없다** → 결근으로 오판 | 기록 없는 근무일은 `미확인(unknown)`으로 두고 결근 확정하지 않음. 사전 등록·보정으로 해소 (§7) |
| L5 | 단말 시계 오차 | NTP 동기화 요구 (§13 I3). 수집 시 서버 시각과의 편차 로깅 |
| L6 | 지문 **원본(생체정보)** 은 개인정보보호법상 민감정보 | MOA는 생체 템플릿을 **일절 저장·수신하지 않는다**. 단말 사용자 ID만 매핑 (§8) |
| L7 | 앱 출근 버튼은 **사외에서도 누를 수 있다** (집에서 미리 누르기) | 지문 시각과 30분 이상 차이 나면 D8 플래그. 사내망 IP 검증은 선택 옵션 (§13 I12) |

> **이 설계의 성립 조건은 하나다 — 퇴근 버튼을 실제로 누르는가.** 지문은 출근 시각의 신뢰할 만한 신호를 주지만 퇴근에 대해서는 아무 정보도 주지 않는다. 연장·야간·주 52시간은 전부 퇴근 시각에서 나오므로, 퇴근 버튼 준수율이 곧 이 모듈의 정확도 상한이다. §5.2의 미기록 처리와 §10의 알림 설계가 그래서 중요하다.


### 4.2 설계 결정

**4.2.1 원본과 판정의 분리** — `att_raw_events`는 append-only. `att_days`는 판정 결과이므로 언제든 재생성 가능한 **파생 테이블**이다. `computed_by_rule_version`을 두어 어떤 규칙으로 계산됐는지 추적하고, 규칙 변경 시 해당 버전 이하만 재계산한다. 03-ERD의 `documents.ydoc_snapshot`(원본) ↔ `text_cache`(파생) 이중화와 같은 철학이다.

**4.2.2 멱등 키** — `UNIQUE(source, external_event_id)`. 단말이 이벤트 ID를 안 주면 `sha256(source|external_user_id|device_id|occurred_at)`로 합성한다. 폴링 구간을 겹치게 잡아도(권장: 마지막 성공 시각 −10분) 중복이 생기지 않는다. 앱 체크는 `moa_app:{user_id}:{direction}:{work_date}` 를 키로 써서 **하루 1건**으로 제한한다 — 퇴근 버튼을 두 번 누르면 나중 것으로 갱신한다(늦게까지 일했다는 뜻이므로).

**4.2.2a 지문과 앱을 한 테이블에 둔다** — `source`로만 구분한다. 지문 이벤트는 `direction='in'` 고정(입장 전용 단말), 앱 이벤트는 `in`/`out` 둘 다 가능하다. 병합 규칙(§5.2)이 한 테이블 안에서 끝나고, 나중에 출구 리더기가 추가돼도 `source='device_out'` 한 줄이면 된다.

**4.2.3 `att_days`를 매일 미리 만든다** — 근무일이면 이벤트가 없어도 `status='unknown'` 행을 생성한다. 행이 없으면 "기록 없음"과 "아직 계산 안 함"을 구분할 수 없고, 결근 누락이 조용히 지나간다.

**4.2.4 연차 잔여를 컬럼으로 들지 않는다** — `leave_balances.used_days`는 승인된 `leave_requests` 합계의 캐시이며, 신청 시점 검증은 실시간 집계로 한다. 15명 규모에서 성능 문제가 없고, 캐시 불일치가 잔여일수 오류로 이어지는 게 더 비싸다.

**4.2.5 인덱스**

```sql
CREATE UNIQUE INDEX uq_raw_events_dedupe ON att_raw_events(source, external_event_id);
CREATE INDEX idx_raw_events_user_time    ON att_raw_events(external_user_id, occurred_at);
CREATE UNIQUE INDEX uq_att_days          ON att_days(user_id, work_date);
CREATE INDEX idx_att_days_date           ON att_days(work_date, status);
CREATE INDEX idx_leave_req_user          ON leave_requests(user_id, start_date DESC);
CREATE INDEX idx_leave_req_pending       ON leave_requests(status, created_at) WHERE status = 'pending';
CREATE INDEX idx_corrections_pending     ON att_corrections(status, created_at) WHERE status = 'pending';
```

**4.2.6 시간대** — 저장은 전부 `timestamptz`(UTC), 판정은 **Asia/Seoul 기준**. `work_date`는 `date` 타입이며 KST 기준 날짜다. 자정을 넘긴 퇴근은 출근일에 귀속한다(§5.6).

### 5.2 출퇴근 시각 결정 — 두 원천 병합

근무시간을 계산하기 전에 `first_in_at`·`last_out_at`을 확정해야 한다. 원천이 둘이므로 우선순위가 필요하다.

**출근 시각** — 지문과 앱 중 **더 이른 쪽**을 채택한다.

```
후보 = { 당일 지문 첫 이벤트, 당일 앱 출근 버튼 }
first_in_at = min(후보)          # 둘 다 없으면 NULL → status='unknown'
in_source   = 채택된 쪽 ('device' | 'app')
```

`min`인 이유는 L2다. 동반 입장으로 아침 지문이 누락되고 점심 후 재입장 시각(13:00)만 남았는데 앱 출근 버튼이 09:00이면, 맞는 값은 09:00이다. 반대로 앱 버튼을 늦게 눌렀고 지문이 09:00이면 09:00이 맞다. **어느 쪽이든 더 이른 기록이 진실에 가깝다** — 사람은 회사에 도착한 뒤에야 두 행위 중 하나를 할 수 있기 때문이다.

이 규칙의 유일한 악용 경로는 출근 전에 집에서 앱 버튼을 누르는 것이다. 지문 시각과 30분 이상 벌어지면 D8 플래그를 세우고, 필요하면 사내망 IP 검증을 켠다(§13 I12).

**퇴근 시각** — 앱 퇴근 버튼이 유일한 원천이다.

```
last_out_at = 당일 앱 퇴근 버튼 시각
            → 없으면 NULL, out_source = NULL, 플래그 D2
```

**미기록 시 자동 추정하지 않는다.** 앱 마지막 활동 시각을 추정치로 *제안*은 하되(보정 신청 화면에 기본값으로 채움), 시스템이 확정하지 않는다. 근무시간은 임금과 직결되므로 추정치가 확정 기록으로 굳으면 분쟁 시 양쪽 모두에게 불리하다. 사람이 확인하고 팀장이 승인한 값만 확정된다.

### 5.2a 근무시간 산정

```
present_minutes = last_out_at - first_in_at            (재실시간)
break_minutes   = 정책 휴게(work_policies.break_minutes) 또는 법정 최소치 중 큰 값
work_minutes    = present_minutes - break_minutes      (0 미만이면 0)
```

`last_out_at`이 NULL이면 **근무시간을 산출하지 않는다.** 0으로 두지도, 정시퇴근으로 간주하지도 않는다. 해당 일자는 `work_minutes = NULL`, 플래그 D2, 월 집계에서 "미확정 N일"로 별도 표시하고 마감 전에 해소를 요구한다.

휴게 공제 규칙:

| 재실시간 | 공제 휴게 |
| --- | --- |
| 4시간 미만 | 0분 |
| 4시간 이상 ~ 8시간 미만 | 30분 |
| 8시간 이상 | max(정책값, 60분) |

> 실제 휴게시간은 측정하지 않는다(L3). 정액 공제가 유일하게 가능한 방식이며, 이는 취업규칙상 휴게시간과 일치해야 한다 → 오픈이슈 **I4**.

### 5.3 연장·야간·휴일 산정

**연장(overtime)** — 일·주 이중 기준의 **중복 계상을 막는다.**

```
일 연장 = max(0, work_minutes - 480)
주 연장 = max(0, Σ(주간 work_minutes) - 2400)
주간 연장 확정치 = max(Σ일연장, 주연장)     ← 합산이 아니라 최댓값
```

일 8시간 초과분은 이미 주 40시간 초과분에 포함되므로 더하면 이중 계상이 된다. 주 단위 마감 시 최댓값으로 확정하고 일별 값은 참고치로 둔다.

**야간(night)** — 재실구간 ∩ [22:00, 익일 06:00]의 분(分). 자정 넘김 시 두 구간(당일 22:00~24:00, 익일 00:00~06:00)의 합.

**휴일(holiday)** — `day_kind`가 `weekly_holiday | public_holiday | company_holiday`인 날의 근무. 8시간 이내/초과로 나눠 각각 집계한다.

> 야간·휴일 시간은 **집계·표시만** 한다. MOA는 급여를 계산하지 않는다 → 오픈이슈 **I6**.

### 5.4 연차 산정 (§60)

| 근속 | 부여 | 비고 |
| --- | --- | --- |
| 입사 1년 미만 | 1개월 개근 시 1일 (최대 11일) | 월 단위 발생 |
| 1년 이상, 출근율 80% 이상 | 15일 | |
| 1년 이상, 출근율 80% 미만 | 1개월 개근 시 1일 | |
| 3년 이상 계속근로 | 15일 + 매 2년마다 1일 가산 | **한도 25일** |

가산 계산: `granted = min(25, 15 + floor((근속연수 - 1) / 2))` (근속 3년차부터 16일)

부여 기준일은 **입사일 기준**과 **회계연도(1/1) 일괄 기준** 중 회사 정책을 따른다 → 오픈이슈 **I5**. `leave_balances.grant_basis`로 둘 다 수용한다.

### 5.5 상태 판정 우선순위

위에서부터 먼저 맞는 규칙으로 확정한다.

| 순위 | 조건 | status |
| --- | --- | --- |
| 1 | 승인된 휴가 존재 | `leave` |
| 2 | 승인된 재택/외근/출장 등록 존재 | `remote` / `trip` |
| 3 | `day_kind ≠ workday` | (휴일 — 근무 있으면 휴일근로 집계) |
| 4 | 출근·퇴근 모두 기록 0건 | `unknown` ← **결근으로 확정하지 않는다** |
| 5 | `first_in_at` 있으나 `last_out_at` NULL | **`incomplete`** ← 퇴근 미기록, 판정 보류 (+D2) |
| 6 | `first_in_at` > 시업시각 + 지각유예 | `late` |
| 7 | `last_out_at` < 종업시각 (유연근무는 코어타임 기준) | `early_leave` |
| 8 | 그 외 | `normal` |

`incomplete`를 지각·조퇴보다 **위**에 두는 이유는, 퇴근 시각이 없으면 그날 판정 자체가 미완이기 때문이다. 지각 여부는 판정 가능하므로 `flags`에 `late`로 함께 기록해 두고, 보정이 승인되면 재계산되어 `late`/`normal`로 확정된다. 화면에서는 `incomplete`가 "⚠ 퇴근 기록 필요"로 눈에 띄게 표시된다.

`absent`(결근)는 **자동 판정하지 않는다.** 관리자가 `unknown` 상태를 검토해 수동 확정한다. 지문 미인식·동반 입장·단말 장애·연동 실패가 결근으로 둔갑하는 것이 이 모듈에서 가장 비싼 오류다.

### 5.6 자정 넘김

앱 퇴근 버튼이 자정 이후에 눌리면 **직전 출근일에 귀속**한다. 익일 03:00 퇴근은 전날 `work_date`의 `last_out_at`이 되고, 익일 `att_days`는 별도 생성한다.

귀속 한계는 `first_in_at + 24시간`이다. 그 이후의 퇴근 클릭은 전날 것으로 보지 않는다 — 전날은 `incomplete`로 남고(D2), 클릭은 당일 이벤트로 처리한다. 퇴근을 잊고 이틀 뒤 누른 경우이므로 보정 신청 대상이다.

## 6. 연동 어댑터 설계

### 6.1 포트 인터페이스

```python
class AttendanceSourceAdapter(Protocol):
    source: str                      # "biostar" | "unis" | "csv" | ...
    def health(self) -> HealthStatus: ...
    def fetch(self, window_from: datetime, window_to: datetime) -> Iterable[RawAccessEvent]: ...

@dataclass(frozen=True)
class RawAccessEvent:
    external_event_id: str | None     # None이면 수집기가 해시로 합성
    external_user_id: str
    device_id: str | None
    direction: Literal["in", "out", "unknown"]
    occurred_at: datetime             # tz-aware
    payload: dict                     # 원본 무손실
```

판정 로직은 `RawAccessEvent`에만 의존한다. 어댑터 교체가 §5에 영향을 주지 않는 것이 이 설계의 목적이다.

### 6.2 어댑터 구현체

| 구현 | 방식 | 적용 상황 | 주의 |
| --- | --- | --- | --- |
| `DbPollingAdapter` | 출입통제 관리 SW의 DB(MSSQL/MySQL 등)를 **읽기 전용** 계정으로 SELECT | BioStar·UNIS 등 관리 SW가 사내 서버에 상주 | 벤더 스키마 변경 리스크. 뷰를 하나 만들어 그것만 조회하는 게 안전 |
| `RestApiAdapter` | 벤더 REST API 폴링 (예: BioStar 2 API) | API·라이선스 보유 시 | 인증 토큰 만료 처리 필수 |
| `CsvImportAdapter` | 관리자가 내려받은 CSV 업로드 | API·DB 접근 불가 시 최후 수단 | 열 매핑 UI 필요, 실시간성 없음 |
| `NullAdapter` | 항상 빈 결과 | 개발·테스트 | |

앱 체크(`source='moa_app'`)는 어댑터가 아니다. MOA 자체 API(§9.1)가 `att_raw_events`에 직접 적재한다. 외부 시스템을 폴링할 필요가 없으므로 어댑터 추상화를 씌우지 않는다.

**개발 순서 — 앱 체크를 먼저 만든다.** 지문 연동은 장비 사양이 미확인이라 언제 붙일지 모르지만(I2), 앱 출퇴근 버튼만 있어도 근태 모듈은 **단독으로 동작한다.** 순서는:

1. 앱 체크인/체크아웃 API + 홈 위젯 → 이 시점에 근태가 실제로 쓸 수 있게 된다
2. 판정 로직(§5) 완성 → 앱 데이터만으로 검증 가능
3. `CsvImportAdapter`로 과거 지문 기록 소급 입력
4. 장비 확인 후 실시간 어댑터 연결 → 출근 시각 정확도가 올라감

지문 연동은 **정확도 개선**이지 **동작 조건**이 아니다. 이 순서면 I2가 계속 미해결이어도 근태가 출시된다.

### 6.3 방향 처리 — 입장 전용 단말

이 회사의 출입문은 **들어올 때만 지문을 찍는다**(P2). 따라서 지문 어댑터가 만드는 이벤트는 전부 `direction='in'`이다. 단말이 IN/OUT 필드를 제공하더라도 실제로는 IN만 발생한다.

| 원천 | direction | 판정에서의 역할 |
| --- | --- | --- |
| 지문 단말 (`device`) | 항상 `in` | 출근 시각 후보. 퇴근에는 기여하지 않음 |
| MOA 앱 (`moa_app`) | `in` / `out` | `in`은 출근 후보(지문 누락 대비), `out`은 **퇴근의 유일한 원천** |
| CSV 임포트 (`csv`) | 파일 규격에 따름 | 과거 데이터 소급 입력용 |

> 향후 출구 리더기를 증설하면(§13 **I11**) `source='device_out'`을 추가하고 §5.2의 퇴근 후보에 `min` 대신 `max`로 합류시키면 된다. 판정 로직의 나머지는 그대로다.

### 6.4 이상탐지 플래그

수집·판정 시 `att_days.flags`에 기록하고 관리자 화면에서 검토 대기열로 노출한다.

| 코드 | 조건 | 의미 | 심각도 |
| --- | --- | --- | --- |
| **D1** | 근무일인데 출근·퇴근 기록 0건 | 미출근 또는 재택/외근 미등록 | 높음 |
| **D2** | 출근은 있으나 **퇴근 미기록** | 앱 퇴근 버튼 미클릭 → `incomplete` | **높음** |
| **D8** | 지문 시각과 앱 출근 시각 차이 > 30분 | 동반 입장으로 지문 누락, 또는 사외 선클릭 | 중간 |
| **D9** | 지문 기록 없이 앱 출근만 있음 | 동반 입장 추정. 정상 처리하되 빈도 집계 | 낮음 |
| D3 | 재실시간 > 16시간 | 퇴근 클릭 누락 후 뒤늦은 클릭 의심 | 중간 |
| D4 | 재실시간 < 1시간 | 잠깐 방문 | 낮음 |
| D5 | 단말 시각 편차 > 5분 | 단말 NTP 이상 | 중간 |
| D6 | 미매핑 `external_user_id` | 신규 입사자 매핑 누락 | 높음 |
| D7 | 동기화 연속 실패 | 연동 장애 | 높음 |

**D2가 이 모듈의 주력 지표다.** 퇴근 미기록률이 높으면 근무시간 통계 전체가 무의미해지므로, 관리 화면 상단에 이번 달 D2 발생률을 상시 노출한다. 10%를 넘으면 앱 버튼 방식 자체를 재검토해야 한다는 신호다(→ 출구 리더기 증설 검토, §13 I11).

**D9는 개인 문책용이 아니다.** 동반 입장은 문이 열려 있으면 자연스럽게 일어나는 일이고, 앱 출근 버튼이 이미 그것을 메우고 있다. D9 빈도는 "출입 정책을 손봐야 하는가"를 판단하는 조직 차원의 신호로만 쓴다.

## 7. 보정·승인 흐름

전자결재가 v1 범위 밖이므로 **신청 → 팀장 1단계 승인**의 경량 흐름으로 고정한다. 결재선·전결 규정·병렬 합의는 없다.

```
[member]  신청 (사유 필수)
            │   notifications(kind='attendance') → 팀장
            ▼
[lead]    승인 / 반려 (반려 시 사유 필수)
            │   notifications → 신청자
            ▼
          att_days 반영 + 이력 보존 (before/after)
```

| 신청 종류 | 대상 | 승인자 | 반영 |
| --- | --- | --- | --- |
| 근태 보정 | 출퇴근 시각 정정 | 팀장 | `att_days` 갱신, 원본 `att_raw_events`는 불변 |
| 휴가 | 연차·반차·병가·경조 | 팀장 | `status='leave'`, 연차 차감 |
| 재택·외근·출장 | 사전 등록 | 팀장 | `status='remote'/'trip'`, 지문 기록 없어도 정상 |
| 연장근로 | 사전 신청/사후 승인 | 팀장 | 미승인 연장은 별도 집계 |

**마감된 월(`locked_at` 설정)** 은 신청이 불가하다. 수정이 필요하면 exec가 마감을 해제해야 하며, 해제 이력이 감사 로그에 남는다.

## 8. 개인정보 처리 (중요)

지문은 **개인정보보호법상 민감정보(생체정보)** 다. 별도 동의와 강화된 보호조치가 필요하다.

| 원칙 | 적용 |
| --- | --- |
| 생체정보 미보관 | MOA는 지문 이미지·템플릿·특징점을 **저장하지도 수신하지도 않는다.** 어댑터는 단말 사용자 ID와 시각만 읽는다 |
| 최소수집 | `att_raw_events.payload`에 생체 관련 필드가 들어오면 **적재 전 제거**한다 (어댑터 책임) |
| 접근통제 | 타인 근태 조회는 lead(팀 한정)·exec만. member는 본인만 (NFR-ATT-02) |
| 목적 제한 | 근태 산정 목적 외 사용 금지. 위치 추적·상시 감시 용도 불가 |
| 보관·파기 | 근기법상 3년 보존, 경과분은 파기. 마감 데이터는 hard delete 차단 |
| 처리방침 고지 | 근태 수집·이용 내역을 사내 개인정보 처리방침에 반영 |

> 생체정보 자체는 기존 출입통제 시스템의 책임 영역이다. MOA는 **파생 이벤트만** 다룬다는 경계를 코드·스키마·문서에서 일관되게 유지한다.

### 10.1 퇴근 버튼의 위치 — 이 모듈의 성패가 걸린 지점

퇴근 버튼을 누르지 않으면 근무시간이 산출되지 않는다(§5.2). 그러므로 버튼은 **찾아 들어가야 하는 곳에 두면 안 된다.**

| 배치 | 규칙 |
| --- | --- |
| 홈 대시보드 | 근태 위젯의 **주 액션 버튼**. 다른 위젯보다 위, 인사 헤더 바로 아래 |
| 모바일 | 홈 상단 고정. 탭 이동 없이 1탭으로 도달 |
| 데스크톱 앱 | 창을 닫을 때 오늘 퇴근 기록이 없으면 **"퇴근 처리하고 종료" 확인** (Tauri 종료 훅) |
| 알림 | 소정 종업시각 +2시간 시점에 미클릭이면 인앱 알림 1회. 익일 아침 홈 배너 |

> 데스크톱 종료 훅이 가장 효과적이다. 대부분의 직원은 퇴근할 때 앱이나 브라우저를 닫는다. 다만 창을 안 닫고 퇴근하는 경우가 있어 알림과 익일 배너가 함께 필요하다. 이 세 겹으로도 D2가 10%를 넘으면 출구 리더기 증설을 검토한다(§13 I11).

## 12. 일정 영향 — 솔직한 평가

**현재 8주 로드맵(M1~M4)에는 근태가 들어갈 자리가 없다.** M1 코어 3주 / M2 커뮤니케이션 2주 / M3 AI 2주 / M4 마감 2주가 모두 다른 기능으로 차 있고, 근태는 WBS에도 없다.

본 설계 기준 순개발량 추정:

| 작업 | 추정 | v1 최소 |
| --- | --- | --- |
| 스키마·마이그레이션, 팀(teams) 추가 | 2일 | ✅ |
| **앱 체크인/아웃 + 홈 위젯 + 종료훅·알림** | **2일** | ✅ |
| 판정 엔진 (§5 전체 + 재계산) | 4일 | 일부 (근무시간만 1일) |
| 어댑터 (CSV + 실시간 1종) | 3일 | ✅ CSV만 1일 |
| API (§9) | 3일 | 2일 |
| 화면 8종 (§10) | 5일 | 3종 2일 |
| 승인 흐름·알림 연동 | 2일 | — |
| 테스트·법정 규칙 검증 | 3일 | 1일 |
| **합계** | **약 24일 (5주, 1인 기준)** | **약 9일** |

오른쪽 열은 "앱 출퇴근 + 월별 조회 + CSV 리포트"만 담은 최소 버전이다. 연차·법정 판정·승인 흐름을 빼면 **9일**로 줄어든다.

선택지는 셋이고, 판단은 기획 몫이다.

| 안 | 내용 | 대가 |
| --- | --- | --- |
| **A. v1.1로 분리** | 9/25 전사 오픈 후 별도 스프린트 | 오픈 시점에 근태 없음. PRD "범위 In"에서 근태를 빼고 v1.1로 명시해야 함 |
| **B. 축소해 M4에 삽입** | 앱 출퇴근 + 조회 + CSV 리포트(9일). 연차·법정 판정·승인 제외 | M4가 2주 → 3.5주. 전사 오픈이 10월 초로 밀림. "근로기준법 대응"은 v1.1 |
| **C. 일정 연장** | 전체 8주 → 12주 | 오픈 10월 하순. 예산·경영진 승인 재보고 필요 |

**권고: B.** 근거는 셋이다.

1. **데이터가 매일 쌓인다.** 늦게 시작할수록 초기 구간이 비고, 오픈 시점에 근태가 없으면 직원들이 기존 방식으로 되돌아간다. 한 번 굳은 습관은 나중에 되돌리기 어렵다.
2. **최소 버전이 9일로 작다.** 앱 출퇴근 버튼과 월별 조회만으로도 "출퇴근이 기록되고 조회된다"는 사용자 가치가 완성된다. 지문 연동은 정확도 개선이지 동작 조건이 아니다(§6.2).
3. **퇴근 버튼 준수율을 미리 측정해야 한다.** 이 설계의 정확도 상한은 D2 발생률이 정한다(§6.4). 법정 판정을 만들어 놓고 나서 "퇴근 버튼을 아무도 안 누른다"를 발견하면 그 작업이 통째로 헛돈다. **먼저 버튼을 깔고 한 달 측정한 뒤 판정 계층을 얹는 순서가 위험이 훨씬 낮다.**

§4 스키마는 처음부터 판정 계층까지 설계해 뒀으므로 v1.1에서 마이그레이션 비용이 들지 않는다.

> 이 권고는 "근로기준법 대응"을 확정한 기획 방향과 충돌한다. 법정 판정까지 8주 안에 넣으려면 정직한 답은 **C(일정 연장)** 다. 축소 없이 일정도 그대로 가는 조합은 존재하지 않는다. 다만 3번 근거 때문에, C를 택하더라도 **앱 버튼을 먼저 배포해 준수율을 측정하는 단계**는 넣는 편이 낫다.
