# frontend

Zenith 웹 프론트엔드. React 19 · Vite · TypeScript · Tailwind v4.

개발 중에는 **MSW**가 `/api/*`를 가로채 목 응답을 준다.

## 실행

```bash
npm install
npm run dev        # http://localhost:5173. 실시간 서버(:1234)도 같이 뜬다
```

| 스크립트 | 설명 |
| --- | --- |
| `npm run dev` | 개발 서버 (MSW 켜짐) + 실시간 서버. 둘을 각각 자식 프로세스로 띄운다(`scripts/dev.js`) |
| `npm run server` | 실시간 서버만 따로. 문서 공동편집 + 채팅. `npm run dev` 가 이미 띄우므로 재시작할 때만 쓴다 |
| `npm run build` | 타입체크 + 프로덕션 빌드 (`dist/`) |
| `npm run typecheck` | 타입만 검사 |
| `npm run lint` | ESLint |
| `npm run preview` | 빌드 결과 미리보기 |

### 실제 백엔드에 붙이기

```bash
VITE_DISABLE_MSW=true npm run dev
```

MSW가 꺼지고 `/api` 요청이 vite 프록시를 통해 `http://localhost:8000`(FastAPI)으로 간다.
8000 이 다른 프로세스에 잡혀 있으면 `.env.local` 에 `VITE_API_TARGET=http://localhost:8010` 처럼 적는다.
백엔드 쪽 준비(DB·마이그레이션·시드)는 [`backend/README.md`](../backend/README.md).

### 인증은 쿠키다

[04 · API 명세서 §1](https://app.notion.com/p/3aaa4716604681a6bba4e0367463e8eb) 그대로다.
로그인은 `POST /api/auth/login` → `204 + Set-Cookie`, 프로필은 `GET /api/me`.
브라우저는 토큰을 갖지 않는다. `access`(15분)·`refresh`(14일)는 HttpOnly 쿠키라 JS 가 읽을 수 없고,
`csrf` 하나만 읽어 상태 변경 요청에 `X-CSRF-Token` 헤더로 되돌려 보낸다(11 §4.3).

- `AuthProvider` 는 마운트 때 **항상** `GET /me` 를 부른다. 200 이면 로그인, 401 이면 익명. 로그인 여부의 판정자는 서버뿐이다.
- `lib/api.ts` 가 `credentials: 'include'` · CSRF 헤더 · **access 만료(`AUTH_EXPIRED`) 시 refresh 후 1회 재시도**를 맡는다. 화면 코드는 신경 쓰지 않는다. 이 규약은 `src/lib/api.test.ts`(`npm test`, vitest)가 고정한다.
- 로그아웃은 서버가 세션을 회수한다. 15분이 남은 access 도 그 즉시 죽는다.
- MSW 모드에서는 `zenith.mock.session=<userId>` 쿠키가 세션을 흉내 낸다. 개발 채팅 서버도 이 쿠키로 사용자를 알아본다.

## 규칙

**API 호출은 반드시 `lib/api.ts`의 `api()`를 거친다.** 쿠키 전송·CSRF 헤더·만료 시 갱신·
에러 정규화(`ApiError`)가 여기 한 곳에 있다. 컴포넌트에서 `fetch`를 직접 부르지 않는다.

**색은 시맨틱 토큰만 쓴다.** `bg-surface`, `text-muted`, `border-line`, `text-accent` 처럼
의미 단위 토큰을 쓰고 `bg-brand-600`, `text-slate-500` 같은 원시값은 쓰지 않는다.
토큰 정의는 `src/styles/index.css`. 라이트/다크 두 벌이 여기서 함께 관리된다.

**폰트 CDN 금지.** 데이터·요청이 사내망을 벗어나면 안 된다. 사내망 밖으로 나가도 되는 호출은
서버의 AI 공급자 하나뿐이고(루트 README 성공 기준, 2026-09-22 재정의) 브라우저는 그 예외에
들지 않는다. Pretendard는 npm 패키지에서 가져와 빌드에 같이 싣는다(`src/main.tsx` 의 import).

**메뉴는 `src/app/navigation.ts` 한 곳에서 정의한다.** 사이드바와 ⌘K 팔레트가 같은 배열을 읽는다.
`minRole`로 메뉴를 숨길 수 있지만 이는 UI 편의일 뿐이고, 실제 차단은 서버 권한 검사가 한다.

**날짜·시간 표기는 `lib/datetime.ts`를 쓴다.** 표기 규칙을 한 곳에 모아 목록·에디터·리포트가
같은 형식을 쓰게 한다.

## 백엔드에 요청한 것

PR 본문에 흩어져 있던 것을 한곳에 모았다. 위는 **없어서 못 하는 것**, 아래는 **계약에 없어서
프론트가 모양을 정한 것**이다. 백엔드가 다르게 정하면 프론트를 고친다.

### 없어서 못 하는 것

- **사람 목록의 등급·팀**(#526): `GET /people` 의 `PersonOut` 에 `role`·`team` 이 있어야 새 기안
  참조자를 임원·사원 두 줄로 가르고(#193) 채팅 프로필 카드에 팀 이름을 보인다(#492). 목만 먼저 주고,
  서버가 안 주면 참조자는 한 줄로, 카드는 팀 줄 없이 보인다. 넣으면 로그인한 누구나 전원의 등급·팀을
  보게 되므로 공개 범위는 백엔드가 정한다.

결재·근태·휴가·휴일·월 마감의 백엔드가 들어왔다(#316). 프론트 목을 그대로 옮긴 계약이고, 아직 안
정해진 #158 항목은 목의 동작을 기본안으로 삼았다(백엔드 README 35·36). 요청했던 결재 임시저장
지우기(#281)와 회사 휴일 이름 고치기(#286)도 들어 있어 스위치를 걷었다. 백엔드가 정한 것 중 화면에
닿는 것: 홈 캘린더의 남의 휴가는 종류를 `leave` 로 가린다(본인과 임원만 원래 종류, 화면은 그냥 휴가로
그린다). 휴일은 회사 휴일만 넣고 고치고 지운다. 정정으로 휴가·휴일 상태는 만들지 않는다. 마감된 달의
근태 문서는 승인도 409 다. 결재선의 임원 순서는 계정을 만든 순이다(목은 두 사람을 박아 뒀다). 휴가
차감 일수는 서버가 휴일까지 빼서 센다(신청 창의 미리보기는 주말만 뺀다). 타입은 아직 손으로 쓴
그대로다.

문서 안 AI(`POST /ai/doc-action`)와 답변 평가(`POST /ai/feedback`)의 백엔드가 들어왔다(#317). 프론트가
부르던 모양 그대로다. 너무 잦은 요청(429 `AI_THROTTLED`, 분당 20회)·시간 초과(503 `AI_TIMEOUT`)·빈 답(503
`AI_EMPTY`)에는 서버 문구를 그대로 띄운다. **AI 가 낸 초안은 마크다운으로 읽되 태그는 글자로 넣는다**
(`features/ai/markdownToHtml.ts`, #393. 굵게·목록·표는 서식이 되고 그림은 대체 글만 남는다). 전에는 그대로 넣어 편집기가 HTML 로 읽었고, 초안에 든
`<img src="https://…">` 가 바깥 주소를 부르는 그림 블록이 되었다. 표 초안과 고정 서식은 전부터
이스케이프했다. `POST /ai/template` 은 서버에 생겼지만 화면은 여전히 고정 서식을 쓴다.

CRM 의 백엔드가 들어왔다(#311, `/crm/*` 열세 경로). 프론트 목을 그대로 옮긴 계약이다. 처음에는
개발 빌드에서만 메뉴를 띄웠다. 지금은 CRM·협업 공간 모두 운영 빌드에서도 연다(실서버 확인은 아직). 서버가
다르게 정한 것에 목을 맞췄다: 검증 실패는 전부 422(설계서가 400 이라 한 사유 누락도), 창구·참석자
배열은 이름순. 아직 안 맞춘 것: 타입이 손으로 쓴 그대로다(`features/crm/types.ts`). 목의 id 는 UUID
가 아니라서 서버가 형식으로 거르는 요청(422)을 목은 404 로 답한다.
프론트가 그 뒤에 만든 셋(안건·담당자 지우기 #305, 지운 기관 되살리기 #312, 가져오기 되돌리기 #315)도
백엔드가 받았다(#318, 이슈 #314). 백엔드가 더 엄격하게 정한 것에 목을 맞췄다: 등록한 사람도 끝난(성사·
중단) 안건과 남이 단계를 옮긴 안건은 못 지우고, 남이 이직 처리한 담당자도 못 지운다. 가져오기 되돌리기는
누가 창구를 맡은 기관을 남긴다. 그 밖의 차이(되돌리기 경합은 409, 가져온 뒤 남이 고친 칸은 같이
사라진다)는 백엔드 README 32번에 있다.

게시글 첨부(#299)도 백엔드가 넣었다(#306). 글쓰기·글 수정 창의 「파일 붙이기」가 운영 빌드에서도
뜬다. 먼저 게시판 경로 밑에 올리고(`POST /boards/{id}/attachments`) 받은 값을 글의 `attachments` 에
싣는다. 백엔드가 정한 것: 올리기와 받기는 그 게시판을 읽을 수 있는 등급만, 글에 싣는 주소는 그
게시판에 올린 파일이고 이름이 같아야 한다(아니면 422), 글 하나에 10개. 자료실에는 싣지 않고 목록에
첨부 여부도 없다. 그림 넷은 inline 으로 온다(화면은 칩만 그린다).
받기 조건(#309)도 백엔드가 넣었다(#323): 그 게시판의 살아 있는 글이 싣고 있는 파일만 받아진다. 글에서
떼거나 글을 지우면 주소를 알아도 못 받는다. 글에 새로 싣는 파일은 올린 사람 본인 것만이다(임원도
같다. 이미 실린 것은 그대로 둘 수 있다). 받기 응답은 브라우저 캐시에 남지 않는다. 목도 이 판정으로
맞췄다.
채팅 첨부도 같은 규칙이 되었다(#327, 이슈 #324): 그 채널의 살아 있는 메시지가 싣고 있는 파일만 받아지고
(메시지를 지우거나 아직 안 보낸 파일은 404), 메시지에 싣는 파일은 그 채널에 내가 올린 것만이며(아니면 소켓
`error` VALIDATION), 받기 응답은 캐시에 남지 않는다. 개발 릴레이(`scripts/chat.js`)도 맞췄다.

게시글 댓글(#292)도 백엔드가 요청한 모양 그대로 넣었다(#303). 글 아래의 댓글 카드가 운영 빌드에서도
뜬다. 백엔드가 정한 것: 열람·작성 권한은 글과 같다(못 읽는 등급은 네 경로 모두 403). 고치기는 쓴
사람만, 지우기는 쓴 사람과 임원(문서 댓글과 다르다. 게시판은 임원이 운영하는 공간이다). 본문의
`@이름` 은 해석하지 않고, 글쓴이에게 가는 알림도 만들지 않는다(등급 밖으로 제목이 새는 길을 처음부터
막는다). 댓글 수와 통합검색은 없다. 글을 지우면 댓글도 같이 사라진다.

홈 캘린더의 내 일정(`/me/events`)도 백엔드가 프론트 목의 모양 그대로 넣었다(#300). 지금까지 실서버에서는
404 였다. `GET /me/events?from=&to=`(둘 다 필수, 366일 이내), `POST`(`{date, title, time?}`), `DELETE`.
`time` 은 `HH:MM` 문자열이다. 고치기는 없다(프론트가 부르지 않는다). 본인 것만 보인다.

빈 폴더 지우기(#271)도 백엔드가 요청한 모양 그대로 넣었다(#298, `DELETE /folders/{id}`). 사이드바
폴더 우클릭 메뉴의 「폴더 지우기」가 운영 빌드에서도 뜬다. 백엔드가 정한 것: 로그인한 누구나 한다
(폴더 만들기·고치기와 같은 기준). 하위 폴더나 문서가 있으면 409 `FOLDER_NOT_EMPTY` 이고, 휴지통에
그 폴더의 문서가 남아 있을 때도 같다(되살릴 자리가 없어진다. 문구는 서버가 준다). 최상위 폴더도
비어 있으면 지워진다.

문서 댓글 고치기(#274)도 백엔드가 요청한 모양 그대로 넣었다(#296). `PATCH /docs/{id}/comments/{comment_id}`
와 `CommentOut.edited_at` 이 실서버에 있고, 내 댓글 줄의 연필 버튼이 운영 빌드에서도 뜬다. 백엔드가
정한 것: 쓴 사람만 한다(기한 없음). 고쳐서 새로 넣은 멘션에는 알림을 만들지 않고, 이미 나간 멘션
알림의 미리보기는 고친 글로 바뀐다(채팅 메시지 고치기와 같은 규칙). 글이 그대로인 요청은 고친
것으로 치지 않는다.

영구 삭제의 조건(#278)도 백엔드가 넣었다(#294). `DELETE /docs/{id}?hard=1` 은 휴지통에 든 문서만
지우고, 아니면 409 `NOT_TRASHED` 다(문서는 그대로). 휴지통 비우기는 그사이 누가 되돌린 문서(409)와
이미 지워진 문서(404)를 실패가 아니라 건드리지 않은 문서로 센다. 지우기 직전에 휴지통을 다시 받던
것은 걷었다. 서버가 문서 행을 잠그고 판정해 되돌리기와 겹쳐도 틈이 없다.

채팅 메시지 고치기·지우기(#264)도 백엔드가 요청한 모양 그대로 넣었다(#284). 소켓 op `edit`·`del`
과 이벤트 `msg_edit`·`msg_del`, `MessageOut.edited_at` 이 실서버에 있고, 내 메시지 줄의 연필·휴지통
버튼이 운영 빌드에서도 뜬다. 백엔드가 정한 것: 쓴 사람만 한다(임원 확대 없음, 기한 없음). 고쳐서
새로 넣은 멘션에는 알림을 만들지 않고, 이미 나간 멘션 알림의 미리보기는 고친 글로 바뀐다. 지우면
그 메시지의 멘션 알림도 같이 지워지고 감사 기록이 남는다(지운 메시지의 첨부 파일은 저장소에
남는다).

채널 이름 바꾸기와 DM 숨기기(#268)도 백엔드가 요청한 모양 그대로 넣었다(#280). 채팅 화면 머리줄의
더보기 버튼이 운영 빌드에서도 뜬다. 백엔드가 정한 것: 이름은 멤버면 누구나 바꾸고(공개 채널은
전원), 바뀌면 감사 기록(`channels.renamed`)이 남는다. 숨김은 그 방에 새 메시지가 오거나 같은
상대와 대화를 다시 열면 풀리고, 다시 열어 풀렸을 때는 본인에게도 `channels` 이벤트가 온다. 홈의
안 읽은 대화 카드도 숨긴 방을 뺀다.

문서 댓글 삭제(#253)와 알림 지우기(#269)는 백엔드가 요청한 모양 그대로 넣었다(#273, #276).
운영 빌드에서도 버튼이 뜬다. 백엔드가 정한 것: 댓글은 쓴 사람만 지운다(임원도 남의 댓글은 못
지운다). 그 댓글에서 나간 멘션 알림도 같이 지워진다. 알림은 내 것만 지워지고 남의 것이나 없는
id 는 조용히 건너뛴다(같은 요청을 두 번 보내도 결과가 같다).

자료실(#226)도 백엔드가 요청한 모양 그대로 넣었다(#240, `GET /archive?limit=`). 운영 빌드에서도
메뉴가 뜬다. 백엔드가 정한 것: 열람 권한은 파일마다 매기지 않고 원래 자리를 따른다(공개 채널과
문서는 전원, 비공개 채널과 DM 은 멤버만. 임원도 멤버가 아니면 못 본다). 문서 자체는 싣지 않고
파일만 싣는다. 문서 쪽은 본문에 지금 붙어 있는 파일이 아니라 **올린 적 있는 파일 전부**다(칩을
지워도 남는다. 붙여 넣은 사진도 실린다). 휴지통에 든 문서와 영구 삭제된 문서의 파일, 결재 첨부는
빠진다. 검색 칸(`q`)과 다음 쪽은 없어서 받아 온 200개 안에서만 이름을 찾는다. 올린 사람은 항상
온다. 서버는 누가 어느 문서 아래에 올렸는지 검사하지 않으므로 **줄마다 올린 사람을 숨기지 않는다**
(좁은 화면에서는 붙은 곳 아래에 보인다).

비공개 채널(#221)은 백엔드가 요청한 모양 그대로 넣었다(#236). 채널 응답의 `is_private`, 만들 때의
`is_private`·`member_ids`, 멤버 더하기·빼기 경로, 소켓 `channels` 이벤트가 실서버에 있다. 백엔드가
정한 것: 멤버면 누구나 더하고 뺀다(연 사람은 본인만 나간다, #352). 비활성 계정은 못 넣는다(422). 임원도 멤버가 아니면 못 본다.
모르는 칸은 422 다. `features/chat/api.ts` 의 `supportsPrivate` 는 #236 이전 서버에 붙었을 때를
위해 남겨 뒀다.

개발 릴레이(`scripts/chat.js`)는 서버보다 느슨하다. 릴레이에서 통과한 요청이 실서버에서도 통과한다고
믿지 않는다. 보내는 본문은 `NewChatModal.test.ts` 가 칸 단위로 고정한다.

- 모르는 칸: 릴레이는 무시하고 서버는 422.
- DM 요청에 비공개 칸이 끼면: 릴레이는 DM 을 만들고 서버는 422.
- 비활성 계정: 릴레이에는 그 개념이 없고 서버는 422.
- 마지막 사람이 나가면: 릴레이는 채널을 지우고 서버는 멤버 0 으로 남긴다(둘 다 목록에서는 사라진다).
- 이미 멤버인 사람만 더하면: 릴레이는 `channels` 이벤트를 보내고 서버는 안 보낸다(화면 차이 없음).

채널 지우기는 프론트가 먼저 만들었고 백엔드가 넣었다(#352). `DELETE /channels/{id}` 이고, 채널 응답에
`can_delete`(내가 지울 수 있는가)와 `created_by`(연 사람, 옛 채널은 `null`)가 실려 온다. 규칙은 공개
채널은 임원, 비공개 채널은 그 채널을 연 멤버(연 사람이 멤버로 없으면 멤버인 임원), DM 은 불가다.
화면은 `can_delete` 가 참일 때만 더보기 메뉴에 지우기를 그린다. 연 사람은 본인만 나갈 수 있어서
(남이 빼면 403) 멤버 창은 그 줄에 빼기를 그리지 않는다. 릴레이도 같은 규칙이다
(공개 채널과 DM 의 `created_by` 는 릴레이가 `null` 로 준다. 화면은 비공개 채널에서만 읽는다).

문서 파일 첨부(#224)도 백엔드가 넣었다(#237). `POST /files` 가 형식을 가리지 않고 받는다. 응답의
`content_type` 은 서버가 파일의 앞 바이트로 판정한 값이고, 프론트는 그 값으로 사진 블록과 파일 칩을
가른다(`features/docs/useFileUpload.ts` 의 `isInlineImage`). 이름의 확장자로 가르면 이름만 `.png` 인
PDF 가 깨진 사진 블록이 된다. 백엔드가 정한 것: 10MB 초과, 빈 파일, 없는 문서나 휴지통 문서의
`doc_id` 는 422. 하루 200개를 넘으면 429. 문서를 영구 삭제해도 파일은 남는다. 목은 형식을 이름의
확장자로 가르므로 위 경우를 목으로는 재현할 수 없다.

전에 남아 있던 멘션 알림의 DM 표시는 백엔드가 답을 줬다(#116, #150). 공개 채널은
채널 이름을 `channel_name` 에 채우고 DM 은 `null` 로 둔다 — 요청했던 모양 그대로다. 다만 #150
이전(09-18~21)에 쌓인 DM 알림 행에는 보낸 사람 이름이 들어 있어, `features/notifications/view.ts`
가 이름이 보낸 사람과 같은 경우도 DM 으로 처리한다. 그 행들이 다 읽히면 걷어낼 수 있다.

### 계약에 없어서 프론트가 정한 것

결재·근태 모듈과 AI 일부는 백엔드보다 프론트를 먼저 만들어, 요청·응답 모양을 프론트가 정했다.
백엔드가 그 뒤에 붙었다(#316·#317). 아직 스텁으로 남은 것은 연차 부여 기준(`/admin/leave-policy`)과
결재 정책(`/admin/approval-policy`) 둘이다. 아래는 그때 프론트가 정한 것의 기록이다.

- **결재**(#108·#110·#111): 종결 상태 이름 `closed` · 강제 종결에 `version` 을 안 보냄 · 종결 사유를
  걸려 있던 단계에 기록 · 기안 요청의 `references: [사람 id]` · 참조 단계의 상태 · 응답의
  `can_decide`(서버가 판정) · 위임 자원과 규칙 전체(자기 자신 422, 거꾸로 된 기간 422, 위임 불가
  유형 422, 겹침 409, 남의 위임 해제 404, 생성 201·해제 204) · "모든 유형" 위임이 그 기간을 독점
- **결재 첨부**(FR-APV-05): 업로드 `POST /approvals/{id}/attachments` multipart `file` → 201
  `{url, name, size, content_type}`(채팅 첨부와 같은 모양), 내 임시저장만(남의 문서 404, 상신 뒤
  409 `NOT_DRAFT`), 빈 파일·10MB 초과 422, 형식 제한 없음 · 내려받기는 응답 `url`
  (`/api/approvals/{id}/attachments/{file_id}/{name}`), 문서 열람과 같은 판정, 뗀 파일 404, 늘
  `attachment` 로 · 저장은 `subject.attachments` 에 **전체 목록**, 새로 만들 때는 빈 목록만, 그
  문서에 올린 파일이 아니면 422(저장 키에 문서 id 를 넣어 판정) · 목 한계: MSW 는 페이지 이동
  요청을 가로채지 않아, 목에서는 첨부 칩을 눌러 받는 것이 안 될 수 있다(판정은 `approvalsDb.test.ts`)
- **결재 서식**(#228): 새 기안의 서식(지출결의서·출장비 결의서·품의서·구매요청서)은 전부 일반 기안(`general`)으로 저장한다. 서식마다 다른 칸의 값은
  `subject.extra: {form, fields: {칸 이름: 글}}`(13 §4.1 `approval_forms.extra`)에 담는다. 서버는
  뜻을 몰라도 되고 받은 그대로 저장해 돌려주면 된다. 같은 내용을 글로 풀어 `subject.body` 에도
  넣어서 읽는 화면은 `body` 만 본다. 칸 구성은 회사 양식이 오기 전의 임시안이다(#158 A5,
  `features/approvals/templates.ts`)
- **근태**(#112·#114): `GET /attendance/me/summary` 응답 `{from, to, summary}`(일자 배열 없음) ·
  기간 상한 366일 · 달력 재생성 응답 `{year, workdays}`
- **AI**(#113): 문서 템플릿(회의록·주간 보고·공지)은 프론트 고정 문안(`features/docs/templateBlocks.ts`)이라
  `POST /ai/template` 을 부르지 않는다. 서버가 `context` 로 채우게 되면 `blocks[]` 한 칸 = **마크다운 한 덩이** 로 붙인다
- 그 밖의 프론트 확장은 각 경로 옆에 적어 뒀다(`?year=`,
  `DELETE /admin/holidays/{date}`, `/leaves/balances`, `scope=all` 등).

### 출퇴근 시각은 기록하지 않는다

[근태 모듈 설계서 v0.3](https://app.notion.com/p/3aea471660468172aea1c46d2b11addf)에서 **출퇴근 시각을 기록하지 않기로**
결정했다(출입문 단말 미연동, 앱 출퇴근 버튼 없음, 전 직원 주 5일 09~18시 고정 근무 전제).
근태는 휴가·연차와 예외 근무(재택·외근·출장·연장) 신청·승인만 다루는 모듈이 된다.

이 결정으로 걷어낸 것은 **v0.2 전제의 실측 화면뿐**이다 — 출퇴근 위젯, 팀 주 52시간 경보
카드(`TeamAlertsCard`), 매 초 현재 시각을 흘리던 `lib/useNow.ts`. 근태 모듈 자체는 v0.3
(신청·승인)으로 다시 구현했고, 화면·목 모두 있다(구현 상태는 위 표 참조).

되살릴 일이 있다면 삭제 직전 커밋(`c4ed480`)에 있다. 다만 경보 카드는 근무시간 실측에 기대는
화면이라 그대로 복구하면 안 된다. 설계서 §5.3의 **승인된 연장근로 신고분 집계**로 다시
만들어야 하고, 화면에 "신고 기준" 라벨을 병기해야 한다(실측처럼 보이면 안 된다).

목 엔드포인트. 백엔드는 같은 스키마로 응답하면 된다.

> 문서 목록·트리·폴더·댓글은 필드 표기까지 계약에 맞췄다(snake_case, `author`·`updated_by` 객체). 아직 남은 어긋남:
>
> - **문서 상세**: `seedHtml` 은 목 전용이다. 백엔드는 그 자리에 `ydoc`(서버 보관 Yjs 상태)을 준다
> - **댓글 멘션**: 필드 표기는 맞췄지만, 서버가 댓글 본문의 @이름으로 만드는 알림을 목은 만들지 않는다. 목의 알림은 고정 씨앗이라 어느 경로도 알림을 새로 만들지 않는다

```
GET   /api/me/home                     대시보드 1콜 { recent_docs, mentions, unread, posts, todos }
                                       `unread[].peer_id` 로 DM 아바타 색을 채팅 목록과 맞춘다(채널은 `null`)
                                       공지는 게시판에서, 멘션은 알림에서, 할 일은 할 일 저장소에서 온다
                                       안 읽은 대화만 개발 릴레이에 물어본다(목은 채팅 상태를 모른다)

GET   /api/me/todos                    오늘 할 일. 만든 순(완료 여부는 정렬에 안 들어간다)
POST  /api/me/todos                    { text } 추가
PATCH /api/me/todos/:id                { text?, done? } 수정. null 은 422
DELETE /api/me/todos/:id               삭제, 204

GET   /api/me/notifications?unread=1   알림함. 권한 밖 글 알림은 제목을 가려서 내려간다
POST  /api/me/notifications/read       { ids[] } 읽음 처리, 204
POST  /api/me/notifications/delete     { ids[] } 지우기(1~200개), 204. 없는 id 는 건너뛴다

GET   /api/search?q=&types=&limit=     ⌘K 통합검색. 배열 그대로 돌려준다({items} 아님)
                                       권한 밖은 마스킹이 아니라 결과에서 빠진다
                                       스니펫은 `**…**` 마커가 든 평문이고 <>& 가 이스케이프돼 온다

GET   /api/tree                        사이드바 트리 { folders[], docs[] }
POST  /api/folders                     { title, parent_id?, sort? }
PATCH /api/folders/:id                 이름·이동·정렬 (프론트는 아직 이름만 쓴다)

GET   /api/trash?limit=                휴지통 목록. 트리의 여집합, 지운 지 최근 순
                                       지운 사람은 `updated_by` 로 온다(따로 주는 칸이 없다)
POST  /api/docs                        { folder_id, title } 생성
DELETE /api/docs/:id                   휴지통으로(30일). ?hard=1 은 임원만, 버전·댓글까지 삭제.
                                       휴지통에 든 문서만 된다(아니면 409 NOT_TRASHED)
POST  /api/docs/:id/untrash            휴지통에서 되돌리기
GET   /api/docs/:id                    메타 (+ seedHtml, 아래 참조)
PATCH /api/docs/:id                    제목·수정시각 투영
GET   /api/docs/:id/comments
POST  /api/docs/:id/comments
DELETE /api/docs/:id/comments/:commentId   쓴 사람만(백엔드 #273)

POST  /api/docs/:id/versions        { snapshot, label? } → 스냅샷까지 실린 버전
POST  /api/docs/:id/restore         { version_id } → 그 버전의 스냅샷. 서버는 되돌리지 않는다
```

### 검색의 목 한계

- **채팅은 목에서 검색되지 않는다.** 메시지가 MSW 가 아니라 개발 릴레이(`scripts/chat.js`)의
  다른 프로세스에 있다. 실제 백엔드에 붙으면 그때 함께 나온다.
- **최근 몇 건 밖의 메시지로는 못 간다.** 백엔드가 주는 `/chat/{채널}?m={메시지}` 를
  `MessageList` 가 읽어 그 줄로 내리고 잠깐 밝힌다. 다만 목록은 최근 것만 내려오고 과거를 더
  불러오는 경로가 없어, 그보다 오래된 메시지면 채널까지만 열린다.
- **일치도 랭킹이 없다.** 실제 서버는 전문검색 점수와 최근성을 더해 매긴다. 목은 부분 문자열
  일치라 점수가 없어 최근순으로만 준다. 그래서 목에서는 "로드맵 목표" 처럼 두 단어를 치면
  0건이지만 실제 서버는 토큰마다 접두 매칭 후 AND 라 결과가 나온다.

## 문서 본문은 서버에 없다

본문의 원천은 **Y.Doc**이다. 서버(MSW)는 목록·검색이 볼 제목과 수정시각, 그리고
버전 스냅샷만 투영해 들고 있다. 실제 백엔드도 같은 모양이 된다. Yjs 업데이트를
보관하고 제목만 별도로 둔다.

> MSW 저장소는 메모리에만 있다. **새로고침하면 버전 기록·댓글이 초기화된다.**
> 문서 본문은 IndexedDB와 개발 서버에 있으므로 그대로 남는다.

지금 동기화 경로는 이렇다.

```
Y.Doc ──┬─ WebSocket              다른 사람 · 다른 브라우저 · 다른 PC
        ├─ BroadcastChannel       같은 브라우저의 다른 탭 (y-websocket 내장)
        └─ IndexeddbPersistence   오프라인 영속
```

### 실행

```bash
npm run dev      # 앱(:5173) + 공동편집·채팅 서버(:1234)
```

**서버가 없으면 다른 브라우저·다른 PC와 동기화되지 않는다.** 같은 브라우저의
탭끼리는 BroadcastChannel로 붙으므로 서버 없이도 되는 것처럼 보이는데, 이게 착시다.
그래서 에디터 헤더에 연결 상태를 항상 띄운다. 서버가 없으면
**"오프라인 편집 중. 이 브라우저에만 저장됩니다"** 가 뜬다. 편집 자체는 계속되고
IndexedDB에 남는다.

### 공동편집 확인하는 법

서버를 켠 상태에서 같은 문서를 **서로 다른 브라우저**(또는 다른 PC)로 열면 된다.
한쪽에서 타이핑하면 다른 쪽에 즉시 반영되고, 상대 커서와 이름표, 헤더의
"N명 편집 중"이 나타난다.

반영 시간은 `scripts/collab-latency.js` 가 잰다 — 클라이언트 두 개를 같은 방에 붙여
A 의 편집이 B 의 Y.Doc 에 도착할 때까지와, 같은 자리 동시 입력이 수렴하는지를 확인한다.
성공 기준 "2인 동시편집 시 1초 이내 변경·커서 반영 (충돌 0)"(01 PRD §5)의 근거는
백엔드 릴레이를 대상으로 잰 값이어야 한다.

```sh
node scripts/collab-latency.js                                # 개발 릴레이(:1234)
node scripts/collab-latency.js --url ws://<서버>/api/yjs \
  --room <문서UUID> --cookie "access=..."                     # 백엔드
```

릴레이 왕복만 잰다. 기준의 "반영"에는 tiptap 렌더도 들어가므로 화면 확인은 위 방법으로 따로 해야 한다.

채팅 전달 시간(07 TC-CHT-01 · NFR-04 "P95 ≤ 500ms")은 `scripts/chat-latency.js` 가 잰다.
두 사람이 각자 소켓을 열고 A 가 보낸 메시지가 B 에게 `ev:msg` 로 올 때까지를 잰다. 보낸 메시지는 채널에
남으니 백엔드에서는 실측용 채널에 쏜다.

```sh
node scripts/chat-latency.js                                  # 개발 서버(:1234)
node scripts/chat-latency.js --url ws://<서버>/api/ws --channel <채널UUID> \
  --cookie-a "access=..." --cookie-b "access=..."             # 백엔드
```

백엔드 소켓은 `access` 쿠키 하나로 사람을 가리고, 그 토큰은 15분이면 만료된다. 방금 로그인해서 받은 값을 넣는다.

2026-09-28 로컬 백엔드(uvicorn + Postgres, 같은 PC) 대상 실측: 공동편집 변경 반영 p95 0.9ms · 최악 4.2ms ·
커서 최악 1.1ms · 충돌 0(`--rounds 100`), 채팅 전달 p50 9.5ms · p95 14.7ms · 최악 40.6ms(`--rounds 200`).
네트워크 구간이 없는 값이라 사내망 서버에서 한 번 더 재면 그 값이 최종 근거다.

### 백엔드가 구현해야 할 것

`scripts/collab.js`가 그 명세다. y-websocket 프로토콜(바이너리, 첫 varuint가
메시지 종류. `0` sync, `1` awareness)이고, 경로 마지막 세그먼트가 문서 ID다.
서버는 문서마다 Y.Doc을 들고 받은 업데이트를 적용·중계한다.

이 개발 서버는 메모리에만 보관한다. **실제 백엔드는 Y.Doc 상태를 영속화해야 한다**.
설계상 문서 본문의 원천이 그 상태다.

앱은 개발 서버 포트에 직접 붙지 않는다. 항상 같은 오리진의 `/api/yjs/{docId}` 로 붙는다.
백엔드 릴레이의 경로 그대로다(04 §4.2, 쿠키 핸드셰이크 인증). MSW 모드에서만 vite 가 이 경로를
개발 릴레이의 `/collab` 으로 넘기고, `VITE_DISABLE_MSW=true` 면 백엔드로 간다(`vite.config.ts`).

`seedHtml`은 Y.Doc이 비어 있을 때만 한 번 심는 초안이다. 실제 서버에서는 보관 중인
Yjs 초기 상태가 그 자리를 대신하므로 이 필드는 사라진다.

> 되돌리기는 `StarterKit`의 `undoRedo`가 아니라 **Yjs UndoManager**가 담당한다
> (`undoRedo: false`). 그래야 Ctrl+Z가 남의 편집까지 지우지 않고 내 변경만 되돌린다.

## 채팅은 MSW를 쓰지 않는다

MSW는 브라우저 안에서만 도는 목이라, A가 보낸 메시지를 B의 MSW는 알지 못한다.
채팅은 공유 상태를 들고 있는 프로세스가 있어야 성립하므로 **개발 서버가 맡는다**
(`scripts/chat.js`).

URL은 백엔드와 같은 `/api/channels*` · `/api/ws` 를 쓴다. MSW는 아래 네 개만 통과시키고
(`handlers.ts`의 `passthrough()`), vite가 개발 서버로 넘긴다(`/api` 를 `/chat` 으로 바꿔서).
백엔드에 붙일 때는 MSW를 끄는 것만으로 전환된다.

통과시키는 경로는 **개발 릴레이가 실제로 여는 것만** 적는다. `/api/channels` 는 프론트가
지어낸 이름이 아니라 백엔드의 네임스페이스라, 아직 안 만든 채널 생성(`POST /api/channels`)이나
첨부(`/api/channels/:id/attachments`)까지 뭉뚱그려 통과시키면 MSW 핸들러가 아예 안 불리고
릴레이의 404로 조용히 떨어진다. 그 둘을 붙일 때는 MSW 핸들러를 새로 만들면 된다.

```
GET   /api/channels                       사용자별 목록 (안읽음·마지막 메시지)
POST  /api/channels                       { name } 공개 채널(전원 멤버) 또는 { dm_user_id } DM
                                          같은 두 사람의 DM 은 하나만. 같은 이름 채널은 409
GET   /api/channels/:id/messages          최근 메시지
POST  /api/channels/:id/messages          전송 (04 에 없다. 백엔드는 WS 의 msg op)
                                          { body, attachments? } 첨부는 먼저 올리고 url 만 싣는다
POST  /api/channels/:id/attachments       multipart `file` → { url, name, size }. 10MB·빈 파일 422
GET   /api/channels/:id/attachments/:fid/:name  내려받기. 멤버만. 이미지는 inline
POST  /api/channels/:id/read              읽음 처리 (04 에 없다. 백엔드는 WS 의 read op)
WS    /api/ws                             message · typing · read 이벤트
```

> 응답 모양(`ChannelOut`·`MessageOut`)은 계약에 맞췄다. 남은 것은 **소켓 이벤트 봉투**
> (`type` → `ev`)와 전송·읽음을 REST 대신 소켓 op 로 옮기는 일이다(backend/README §4.1 (g)).

전송은 REST로 하고 **화면 반영은 전부 WebSocket이 한다**. 내가 보낸 메시지도
서버를 한 바퀴 돌아 같은 경로로 돌아온다. 낙관적 추가를 하지 않으므로 다른 탭·다른
사람과 순서가 어긋나지 않는다.

> 인증은 MSW 로그인이 심는 `zenith.mock.session` 쿠키로 한다. 실제 백엔드가 HttpOnly 쿠키의
> JWT 에서 사용자를 꺼내는 것과 같은 자리다. 채널 멤버가 아닌 요청은 403이어야 한다.
> 대화는 메모리에만 있어 서버를 끄면 사라진다.

## 버전 기록과 되돌리기

편집이 5초간 멎으면 스냅샷을 남긴다. 같은 사람이 이어서 편집하는 동안은 서버가
3분 단위로 하나로 접는다. 접지 않으면 타이핑을 멈출 때마다 버전이 쌓여 기록을
읽을 수 없다. 되돌리기처럼 이유가 분명한 버전에는 라벨이 붙고, 라벨이 붙으면 접히지 않는다.

**Yjs 스냅샷은 내용 사본이 아니라 시점 표식이다.** 실제 내용은 Y.Doc이 들고 있는
이력에서 되살린다. 그래서 서버가 보관하는 스냅샷은 작지만, 대신 두 가지가 전제된다.

- **`gc: false`**. 클라이언트(`useCollabSession.ts`)와 서버(`scripts/collab.js`)
  **양쪽 모두**. 한쪽이라도 삭제 내용을 수거하면 과거 버전을 복원할 수 없다.
  대신 문서가 계속 커진다. 15명 규모 위키에서는 감수할 만한 비용으로 봤다.
- 복원은 **클라이언트에서** 한다. 서버는 스냅샷만 들고 있고 이력은 Y.Doc에 있다.

### 되돌리기는 되감기가 아니다

Y.Doc을 과거 상태로 갈아끼우면, 접속 중인 다른 사람의 상태와 병합되면서 되돌리기가
도로 취소된다. 그래서 스냅샷 시점의 내용을 ProseMirror JSON으로 꺼내
`editor.commands.setContent()` 로 **앞으로 나아가는 편집 한 번**으로 넣는다.

이러면 모두가 같은 결과로 수렴하고, 되돌리기 자체도 Ctrl+Z로 취소할 수 있으며,
되돌리기 전 버전도 기록에 그대로 남아 다시 앞으로 갈 수 있다.
